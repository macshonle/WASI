# WASI Repository Exploration Notes

This document captures findings from exploring the WebAssembly System Interface (WASI) repository structure, build system, and documentation generation.

## Repository Overview

This is a **specification repository**, not a code implementation. It defines the WebAssembly System Interface (WASI) using WIT (WebAssembly Interface Types) files. There is no traditional build system (no Cargo.toml, package.json, etc.) because the primary artifacts are interface definitions, not compiled code.

## Directory Structure

```
/
├── proposals/           # WASI proposals (cli, clocks, filesystem, http, io, random, sockets)
│   └── {proposal}/
│       ├── wit/              # Stable WASI 0.2.x interface definitions
│       │   ├── *.wit         # Interface definition files
│       │   ├── deps.toml     # wit-deps dependency manifest
│       │   └── deps.lock     # wit-deps lock file
│       ├── wit-0.3.0-draft/  # Draft WASI 0.3.0 definitions (not in io)
│       ├── test/             # Test suite
│       ├── command.md        # Generated documentation (from world command)
│       ├── imports.md        # Generated documentation (from world imports)
│       └── README.md         # Manual documentation
├── docs/                # High-level documentation
├── specifications/      # Released specification versions (wasi-0.2.0 through 0.2.9)
├── .github/
│   ├── workflows/       # CI/CD pipelines
│   ├── scripts/         # Release and validation scripts
│   └── actions/         # Custom GitHub Actions
└── assets/              # Logo and branding
```

## The WIT Files

There are approximately 33 non-draft `.wit` files defining WASI interfaces. Each file contains:

- **Interface definitions** with types, functions, and resources
- **Documentation comments** using `///` triple-slash syntax
- **Version annotations** using `@since(version = X.Y.Z)` or `@unstable(feature = ...)`

Example from `proposals/cli/wit/exit.wit`:
```wit
@since(version = 0.2.0)
interface exit {
  /// Exit the current instance and any linked instances.
  @since(version = 0.2.0)
  exit: func(status: result);

  /// Exit the current instance and any linked instances, reporting the
  /// specified status code to the host.
  @unstable(feature = cli-exit-with-code)
  exit-with-code: func(status-code: u8);
}
```

## Documentation Generation: WIT to Markdown

**Key Discovery:** The `.md` files like `command.md` and `imports.md` are **auto-generated** from WIT files.

### The Tool: wit-bindgen

The documentation is generated by `wit-bindgen`, a tool from the Bytecode Alliance:
- Repository: https://github.com/bytecodealliance/wit-bindgen
- Version used: 0.48.1

### How It Works

1. WIT files define "worlds" - groupings of imports and exports
2. Each world generates a separate markdown file
3. The `///` doc comments become prose documentation

**Example from `proposals/cli/wit/command.wit`:**
```wit
world command {
  include imports;
  export run;
}
```

**Example from `proposals/cli/wit/imports.wit`:**
```wit
world imports {
  import environment;
  import exit;
  // ... more imports
}
```

### command.md vs imports.md

- **`command.md`**: Generated from `world command` - includes both imports AND exports (exports the `run` interface)
- **`imports.md`**: Generated from `world imports` - includes only imports (no exports section)

Both files are generated from the same underlying interfaces, so much of their content is identical. The difference is:
- `command.md` represents a full CLI application world
- `imports.md` represents just the available imports without requiring the run export

### Generation Command

From `.github/workflows/release.yml` (lines 159-178):
```bash
wit-bindgen markdown "$wit_path" -w "$world" --html-in-md --all-features --out-dir "proposals/$proposal"
```

Flags:
- `-w "$world"`: Which world to generate docs for
- `--html-in-md`: Output HTML tags in markdown (for anchors and formatting)
- `--all-features`: Include unstable features

### When Documentation is Generated

Documentation is **only regenerated during patch releases (0.2.x)**, not during RC releases (0.3.0-rc-*). This happens in the `release.yml` workflow when `release_type == 'patch'`.

## Container References Explained

The container references like:
```
ghcr.io/webassembly/wasi/io:0.2.0
```

Are **OCI (Open Container Initiative) registry packages** containing the WIT definitions as WebAssembly binary artifacts. These are:

1. **Built** using `wkg wit build` (Wasm Kit)
2. **Published** to GitHub Container Registry (GHCR) during the publish workflow
3. **Consumable** by tools that understand WIT/WASM packages

They are NOT Docker containers - they use OCI as a distribution mechanism for WASM packages.

### Recommended Local Installation

For working with this repository locally, install these tools:

```bash
# Essential tools
cargo install wasm-tools        # Validates WIT syntax
cargo install wit-deps-cli      # Fetches WIT dependencies (REQUIRED before validation)
cargo install wit-bindgen-cli   # Generates markdown documentation

# Optional but useful
cargo install wkg               # Build WIT packages locally (for OCI publishing)
```

**Important:** Most proposals have dependencies on other proposals. You must run `wit-deps` to fetch dependencies before `wasm-tools` can validate them. The `io` and `random` proposals have no dependencies and can be validated directly.

## What Can Be Built/Run/Tested Locally

### Validate a Simple Proposal (no dependencies)

The `io` and `random` proposals have no WASI dependencies and can be validated directly:

```bash
wasm-tools component wit proposals/io/wit
wasm-tools component wit proposals/random/wit
```

### Validate a Proposal with Dependencies

Most proposals depend on others. You must fetch dependencies first:

```bash
# Step 1: Fetch dependencies (creates/updates the deps/ directory)
wit-deps -m proposals/cli/wit/deps.toml -l proposals/cli/wit/deps.lock -d proposals/cli/wit/deps update

# Step 2: Now validation will work
wasm-tools component wit proposals/cli/wit
```

Without step 1, you'll see errors like `package 'wasi:io@0.2.9' not found`.

### Generate Documentation

```bash
# Generate docs for the 'command' world
wit-bindgen markdown proposals/cli/wit -w command --html-in-md --all-features --out-dir proposals/cli

# Generate docs for the 'imports' world
wit-bindgen markdown proposals/cli/wit -w imports --html-in-md --all-features --out-dir proposals/cli
```

### Build a WIT Package (for OCI)

```bash
# Build a .wasm package from WIT definitions
wkg wit build -o wasi-cli.wasm --wit-dir proposals/cli/wit
```

### Run CI Validation Scripts

```bash
# Requires Node.js, wasm-tools, and wit-deps
WIT_02_FILES='["proposals/cli/wit/cli.wit"]' node .github/scripts/validate-proposals.js
```

## Versioning

- **Stable**: `0.2.x` in `wit/` directories
- **Draft**: `0.3.0-rc-YYYY-MM-DD` in `wit-0.3.0-draft/` directories
- The `io` proposal is excluded from 0.3.0-rc releases

## Summary

The WASI repository is a specification project where:
1. **WIT files are the source of truth** for interface definitions
2. **`wit-bindgen markdown`** generates the API reference documentation (command.md, imports.md)
3. **`wkg`** packages and publishes definitions to OCI/GHCR
4. **GitHub Actions** automate validation, releases, and publishing
5. No traditional build system exists - this is a spec repo, not an implementation

### Quick Start

```bash
# Install the essential tools
cargo install wasm-tools wit-deps-cli wit-bindgen-cli

# Validate a simple proposal (no deps)
wasm-tools component wit proposals/io/wit

# Validate a complex proposal (has deps)
wit-deps -m proposals/cli/wit/deps.toml -l proposals/cli/wit/deps.lock -d proposals/cli/wit/deps update
wasm-tools component wit proposals/cli/wit

# Generate documentation
wit-bindgen markdown proposals/cli/wit -w command --html-in-md --all-features --out-dir proposals/cli

# Generate C bindings (uses Makefile)
make v0.2.0
```

## Generating C Bindings

A Makefile is provided to generate C bindings from the WIT files. This is useful for implementing WASI in C.

### Usage

```bash
# Generate C bindings for WASI v0.2.0
make v0.2.0

# Generate bindings from current HEAD (latest)
make

# Generate bindings for a specific proposal
make proposal-io
make proposal-cli

# Clean generated files
make clean

# Show all available targets
make help
```

### Output Structure

```
build/c-bindings/
├── io/           # wasi:io interfaces
│   ├── imports.c
│   ├── imports.h
│   └── imports_component_type.o
├── random/       # wasi:random interfaces
├── clocks/       # wasi:clocks interfaces
├── filesystem/   # wasi:filesystem interfaces
├── sockets/      # wasi:sockets interfaces
├── cli/          # wasi:cli interfaces
│   ├── cli_imports.c/h    # CLI imports only
│   └── command.c/h        # Full command world (imports + run export)
└── http/         # wasi:http interfaces (proxy world)
```

### Generated Files

Each proposal generates:
- `*.h` - C header with type definitions, function declarations
- `*.c` - C implementation stubs and helper functions
- `*_component_type.o` - Object file containing component type information

### Version Differences

- **v0.2.0**: Uses older `preview2/` directory structure. All WIT packages must be passed together.
- **v0.2.1+**: Uses modern `proposals/*/wit/` structure with `deps.toml` for dependency management.
